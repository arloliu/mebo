### Test Data

The main tables use one mixed blob, because a blob's value encoding applies to every metric in it,
so the right codec is the one that does best on the metrics a real blob holds together:

Mixed blob, 15 s scrape interval:

- 35% of metrics: 2-decimal gauge, steps up to ±0.5%, 30% of points repeat the previous value
- 20% of metrics: integer counter, +1 to +10 per point
- 18% of metrics: mostly-constant 2-decimal value, a small step on 5% of points
- 27% of metrics: full-precision gauge, steps up to ±0.5%
- Timestamps: 96% exactly on the scrape grid, the rest 2–10 ms off

The mix is calibrated, not measured:
its shares are chosen so that Chimp, the codec used in production today,
costs about 3.8 bytes/point at 100 metrics × 150 points with shared DeltaPacked timestamps (the owner's calibration target),
and repeats are common, as in Facebook's production data,
where about 51% of values equal the previous one (Gorilla, PVLDB 2015, §4.1.2).
One aggregate figure cannot pin down four shares,
so [Codec Selection by Data Shape](#codec-selection-by-data-shape) also measures three other mixes calibrated the same way,
and the single-kind profiles behind them.
Replace the shares with real proportions when they are known (`tests/measurev2/types.go`).

### Timing Method

Layout-averaged `testing.Benchmark`: 4 code layouts × 4 rounds,
16 runs per cell at a 50ms benchtime,
pinned to CPU 6 (AMD Ryzen 9 9950X3D 16-Core Processor) with GOMAXPROCS=1;
every data set measured in one process per run.
The layouts vary the placement of the repository's code only, not the runtime's or the standard library's.
Each cell reports the median of its runs.
A speed comparison is **decided** only when the gap is at least 20% and every layout's median puts the same combo ahead;
a gap under 20% is **equivalent**, and a larger gap that not every layout supports is **inconclusive**.
Pinning one core with GOMAXPROCS=1 puts the garbage collector on the measured core,
so allocation-heavy operations read slower than in reports measured without pinning.
‡ marks a cell whose allocs/op differed between runs; the median is shown.

### Running Benchmarks

```bash
# Every table of this report: four code layouts × 4 rounds, pinned, merged into OUTDIR/merged/
tests/measurev2/layouts.sh -o $TMPDIR/perf -cpu 6 -benchtime 50ms -cells report -rounds 4

# Via Makefile (the same command with its defaults)
make bench-report
```

### Key Observations

- **ALP-RLE is the smallest value codec on this mix.**
  Shared DeltaPacked + ALP-RLE takes 2.593 bytes/point,
  32.6% less than Shared DeltaPacked + Chimp (3.846) and 8.1% less than plain ALP (2.822).
  Its gain over ALP comes from the held gauges and the mostly-constant metrics, the only parts of the mix with repeats.
- **Shared timestamps save about 1.2 bytes/point here**, whatever the value codec:
  Delta + Raw is 9.340 bytes/point and Shared Delta + Raw 8.134.
  That is 31.8% of Delta + ALP-RLE (3.797 → 2.591) and 23.9% of Delta + Chimp (5.050 → 3.844).
  Without shared timestamps, Delta + ALP-RLE (3.797) is already 1.3% smaller than Shared DeltaPacked + Chimp,
  so the value codec alone recovers what shared timestamps save.
- **With shared timestamps, the timestamp encoding hardly changes the size**:
  Shared Delta, DeltaPacked and Raw + ALP-RLE take 2.591, 2.593 and 2.660 bytes/point.
  Per metric, DeltaPacked costs 0.200 bytes/point more than Delta (3.997 vs 3.797 with ALP-RLE),
  and Raw timestamps cost 6.769 more (10.566).
- **Encoding is the ALP family's cost.**
  Shared DeltaPacked + ALP-RLE encodes in 314,970 ns/op (21.0 ns/point), 1.82× Chimp's 173,061 (11.5 ns/point);
  plain ALP takes 247,500 ns/op, 1.43× Chimp, and ALP-RLE takes 1.27× plain ALP; all three comparisons are decided.
  Across the profiles below, ALP-RLE's encode time is equivalent to Chimp's on `decimal_gauge_2dp` only
  and 1.37× (`decimal_gauge_4dp`) to 2.58× (`sparse_constant`) Chimp's elsewhere.
  These runs use the AVX-512 exponent search;
  CPUs without AVX-512DQ run the scalar search and encode the ALP family several times slower
  (see [the search design](specs/alp-simd-ef-search-design.md#results)).
- **Reads are faster with ALP-RLE, except for opening the blob.**
  `ValueAt` takes 2,151 ns/op against Chimp's 48,707 (22.6× faster),
  because Chimp decodes its XOR chain from the start of the column.
  Iteration takes 84,811 against 109,732 ns/op (1.29× faster).
  Opening the blob takes 4,924 against 3,578 ns/op (1.38× slower), about 1.4 µs more per blob.
- **DeltaPacked and Delta timestamps iterate equivalently with every compressed value codec.**
  Shared DeltaPacked + Chimp takes 109,732 ns/op and Shared Delta + Chimp 105,839;
  Shared DeltaPacked + Gorilla takes 94,099 and Shared Delta + Gorilla 94,023;
  with ALP-RLE, 84,811 and 83,125; all three pairs are equivalent.
  With Raw values DeltaPacked is the faster of the two, 1.45× (Shared, 55,630 against 80,916 ns/op),
  because its timestamps are decoded a whole column at a time;
  DeltaPacked + Raw (54,449) and Shared DeltaPacked + Raw iterate fastest of all 30 combos,
  at 3.1–3.7× ALP-RLE's size (9.540 and 8.136 bytes/point).
  Among the compressed codecs, ALP-RLE iterates 1.29× faster than Chimp and is equivalent to Gorilla.
- **Shared `TimestampAt` reads 935–943 ns/op** across the 15 shared combos, whatever the codecs:
  the pre-decoded shared column is found by an inlined group lookup
  (`specs/index-entry-by-pointer-design.md`, "Follow-up");
  per-metric Delta and DeltaPacked timestamps take 12,888–13,009 and 9,484–9,601 ns/op, decoded from the column's start.

## Random Access Performance

`ValueAt`/`TimestampAt` at a uniformly random index per metric
(see `randomAccessPattern` in `tests/measurev2/bench.go`).
One op looks up one point in each of the blob's 100 metrics, so ns/op covers 100 lookups.
The encodings differ in complexity, not just in constants:

| Encoding | `At()` complexity | Why |
|---|---|---|
| Raw (timestamp or value) | O(1) | Direct offset into a fixed-width array |
| ALP (value) | O(1) + O(log k) | O(1) windowed bit read, plus binary search over that column's exception sidecar (k = exceptions in that column, not n) |
| ALP-RLE (value) | O(index/64) + O(log k) | A column with repeats ranks the run-start bitmap one 64-bit word at a time (at most 3 popcounts at 150 points), then reads that run like ALP; a column without repeats is plain ALP |
| Delta / DeltaPacked (timestamp) | O(index) | Must sequentially decode every delta from the start — each value depends on the accumulated sum before it |
| Shared timestamps (any encoding) | O(1) | Decoded once into a cache when the blob is opened; `TimestampAt` reads the cache |
| Gorilla / Chimp (value) | O(index) | Must sequentially decode the XOR chain from the start of the column |

A uniformly random index makes the O(index) encodings pay their average cost across a column,
not a best case (index 0) or worst case (last index).

### Key Insights

All figures are `mix_monitoring` with Shared DeltaPacked timestamps.

- **ALP-RLE overtakes Chimp between 5 and 10 points per metric.**
  At 5 points ALP-RLE takes 8.770 bytes/point and Chimp 8.364;
  at 10 points ALP-RLE takes 5.633 and Chimp 6.066.
  The ALP family pays about one byte more per metric up front (27.440 against 26.440 bytes/point at a single point).
- **The gap widens as columns grow**:
  ALP-RLE is 18.3% smaller than Chimp at 20 points, 28.3% at 50, 31.4% at 100 and 32.6% at 150.
- **Runs need length.**
  ALP-RLE and ALP are identical up to 10 points;
  from 20 points on ALP-RLE pulls ahead, reaching 8.1% at 150 (2.593 against 2.822).
- **Overhead against the 150-point size**: ALP-RLE is 55% higher at 20 points, 16% at 50 and 4% at 100;
  Chimp is 28%, 9% and 2% higher.
  Chimp flattens sooner because its fixed cost is a smaller share of a larger per-point cost.
- **150 points is the largest length measured, and ALP-RLE still falls 4% from 100 to 150**;
  longer columns may shrink it further, but this run measured none.

### ALP-RLE speed, layout-averaged

ALP-RLE (`format.TypeALPRLE`) is ALP with a run-length front end.
For each column, the encoder keeps a runs layout (a run-start bitmap plus one ALP value per run)
only when it is smaller than the plain ALP column, so each uncompressed column is never larger than under ALP.
It targets columns where many points repeat the previous value,
where plain ALP loses to the XOR codecs above (`sparse_constant`, and the repeating full-precision metrics in `mix_fullprec`).
When to pick it, and its compatibility cost, are in [Best Practices § ALP or ALP-RLE?](best_practices.md#alp-or-alp-rle).

**Provenance:** these speeds come from codec- and blob-level Go benchmarks, not from `tests/measurev2`,
with shared DeltaPacked timestamps, no compression and no tags.
They are layout-averaged to remove code-placement noise: 4 code layouts × 3 rounds, medians of n = 12,
`taskset -c 6`, `-test.cpu 1`, AMD Ryzen 9 9950X3D, Go 1.26.7, 2026-10-11;
benchmarks `BenchmarkALPRuns_*` in `internal/encoding/value/alp/alp_runs_bench_test.go`
and `BenchmarkALPRLEGate_*` in `blob/numeric_alp_bench_test.go`.
The encoder searched ALP's exponents with the AVX-512 kernels of [`specs/alp-simd-ef-search-design.md`](specs/alp-simd-ef-search-design.md),
and the decoder unpacked whole ALP columns with the AVX-512 VBMI kernel added in v1.13.0.
The encode rows add each metric with one `AddDataPoints` call, while `tests/measurev2` adds one point at a time,
so their ratios against Chimp are not the profile tables' ratios.
The design, the gates these numbers were judged against, and the method are in
[`specs/alp-rle-design.md`](specs/alp-rle-design.md).

Speed on a 2-decimal gauge where half the points repeat (the `cal_2dp_hold50` shape, from the benchmarks' own generator), 100 metrics × 150 points.
The encode row without forced repeats uses the same gauge with no holds; no column there takes the runs layout.

| measurement | level | Chimp | ALP | ALP-RLE | ALP-RLE vs ALP | ALP-RLE vs Chimp |
|---|---|---:|---:|---:|---:|---:|
| `DecodeAll`, ns/point | codec | 2.67 | 0.30 | 0.70 | 2.37× | 3.8× faster |
| `At`, ns/lookup | codec | 413 | 7.3 | 13.2 | 1.82× | 31× faster |
| `ValueAt`, ns/lookup | blob | 414 | 17.6 | 22.5 | 1.28× | 18× faster |
| `ForEachValues`, ns/point | blob | 4.79 | 2.68 | 3.06 | 1.14× (equivalent) | 1.6× faster |
| `Materialize`, ns/point | blob | 4.35 | 1.79 | 2.22 | 1.24× | 2.0× faster |
| encode, half the points repeat, µs/blob | blob | 94 | 184 | 327 | 1.77× | 3.5× slower |
| encode, no forced repeats, µs/blob | blob | 115 | 187 | 194 | 1.04× (equivalent) | 1.7× slower |

- Every read path is faster than Chimp's.
  ALP-RLE decodes in two passes (the nested ALP column, then the run expansion),
  so its `DecodeAll` takes 2.37× plain ALP's time;
  the AVX-512 decode kernel speeds up only the first pass.
  At blob level the gap is smaller: `Materialize` takes 1.24× plain ALP's time, and `ForEachValues` is equivalent (1.14×).
- Encoding costs more: a runs column needs a second ALP encode of the run values,
  so with half the points repeating ALP-RLE takes 1.77× plain ALP's time.
  On data without repeats, the encoder skips that attempt and the two are equivalent (1.04×).
- Against Chimp, ALP-RLE's encode takes 3.5× the time with half the points repeating and 1.7× without forced repeats.
  The profile tables above, which add one point at a time, measure 2.0× on `cal_2dp_hold50`
  and an equivalent encode time on `decimal_gauge_2dp`.
- With value compression (Zstd, S2, LZ4) the codec runs over the whole value payload,
  and a smaller input is not guaranteed to compress smaller.

### Takeaways

Sizes below are Shared DeltaPacked bytes/point from the tables above;
timings come from the profile runs, which time the Shared DeltaPacked combos and Delta + Gorilla.

- **ALP-RLE is the smallest value codec on all four mixes**, against Chimp:
  32.6% smaller on `mix_monitoring`, 46.3% on `mix_sensor`, 47.5% on `mix_integer` and 12.8% on `mix_fullprec`.
  All four cost Chimp about the same (3.808–3.912 bytes/point), yet the saving ranges from 12.8% to 47.5%,
  so the shares of each metric kind decide how much ALP-RLE saves, though not which codec wins.
  The saving is smallest where full-precision metrics dominate (65% of `mix_fullprec`).
- **On the single-kind profiles, ALP-RLE is smallest or tied with ALP everywhere except full-precision data without repeats.**
  It is byte-identical to ALP on `counter`, `decimal_gauge_2dp` and `decimal_gauge_4dp`,
  and 4.7% (`cal_2dp_step0.005`) to 62.9% (`sparse_constant`) smaller than ALP on the profiles with repeats.
  On `worst_case` it is 2.0% larger than Chimp (6.512 against 6.384), and on `legacy_random_walk` 1.6% larger.
  Measured against Chimp, ALP-RLE gives up at most about 2% on any profile here and saves 12.8–80.3% on the rest.
- **Plain ALP has two traps, and ALP-RLE closes both.**
  On `sparse_constant` ALP takes 1.244 bytes/point, 1.95× Gorilla's 0.638.
  On `mix_fullprec` it takes 4.699, 20.1% more than Chimp's 3.912,
  because the XOR codecs store a repeat in about one bit, while ALP encodes a repeated value like any other.
  Pick plain ALP over ALP-RLE when readers cannot decode ALP-RLE yet,
  or when encode time matters more than the runs saving,
  and in either case not for blobs dominated by mostly-constant metrics or with repeating full-precision ones.
  On shapes with few repeats ALP stays close to ALP-RLE's size and encodes faster:
  on `cal_1dp_step0.03` it takes 0.830 bytes/point against 0.789 (5.1% more)
  and encodes in 15.11 ns/point, against 20.65 for ALP-RLE (1.37× faster) and 12.84 for Chimp (equivalent).
- **Repeats decide ALP-RLE's lead over ALP**: on the 2-decimal gauge it is 17.0% smaller with 30% of points repeating,
  33.1% with 50% and 49.6% with 70%,
  and on those three it takes 1.62–1.66× plain ALP's encode time.
- **Random access favors the ALP family on every profile; iteration on most; encoding is its cost.**
  `ValueAt` is 9.3× (`sparse_constant`) to 36.7× (`decimal_gauge_2dp`) faster with ALP-RLE than with Chimp, all decided.
  ALP-RLE iterates faster than Chimp on 13 profiles,
  1.29× (`mix_sensor`) to 1.73× (`decimal_gauge_4dp`),
  and is equivalent to it on `cal_1dp_step0.01`, `cal_2dp_hold70` and `sparse_constant`.
  Against Gorilla it iterates 1.28–1.38× faster on `counter`, `cal_1dp_step0.03`, `cal_2dp_hold30`, `cal_2dp_hold50`
  and `cal_2dp_step0.005`, and is equivalent everywhere else, the four mixes included.
  The ALP family iterates at 5.07–6.19 ns/point on every profile;
  the XOR codecs range wider (Gorilla 4.63–7.59, Chimp 4.85–8.90).
  Raw values iterate faster than the ALP family on every profile (3.70–3.74 ns/point, 1.36–1.66× faster than ALP-RLE)
  at 8.135–8.144 bytes/point, so they pay off only where bytes do not matter.
  On `sparse_constant`, per-metric Delta + Gorilla iterates 1.32× faster than Shared DeltaPacked + ALP-RLE
  (62,954 against 83,366 ns/op).
  ALP-RLE's encode time is equivalent to Chimp's on `decimal_gauge_2dp`,
  and 1.37× (`decimal_gauge_4dp`) to 2.58× (`sparse_constant`) Chimp's on the other profiles.
  Without repeats it encodes the same columns as ALP, so the 1.02–1.03× gaps there are noise;
  with repeats it takes up to 1.66× ALP's time (`cal_2dp_hold70`),
  and the [layout-averaged codec benchmarks](#alp-rle-speed-layout-averaged) measure 1.77× on the half-repeated gauge.
- **Neither XOR codec wins everywhere.**
  Gorilla is smaller on `counter` (1.723 against 2.066), `sparse_constant` (0.638 against 0.742),
  `cal_1dp_step0.01` (2.012 against 2.066) and `cal_2dp_hold70` (2.165 against 2.184);
  Chimp is 0.8–2.6% smaller on the four mixes.
  Their encode times are equivalent on most profiles;
  Chimp takes 1.22–1.26× Gorilla's on `legacy_random_walk`, `decimal_gauge_2dp`, `decimal_gauge_4dp` and `worst_case`,
  and Gorilla iterates 1.47–1.50× faster than Chimp on those four
  and 1.21× on `mix_integer` and `cal_1dp_step0.03` (equivalent elsewhere).
- **A blob applies one value codec to all its metrics**, so a mixed blob always pays for its worst-fitting part.
  Per-column codec selection would remove that trade-off;
  see [`adaptive_selector_experiments.md`](perf/adaptive_selector_experiments.md)
  and the [implementation plan](plans/2026-06-15-adaptive-value-codec-selection.md).
  It is not wired yet.

## Choosing an Encoding Strategy

### Decision Tree

Numbers are bytes/point on `mix_monitoring` unless the branch names another data set.
Every Shared leaf needs V2 readers;
without them, keep the value codec and use Delta timestamps (Delta + ALP-RLE 3.797, Delta + Chimp 5.050).

```
What do the blob's metrics hold?
├─ Decimal values, counters or repeats (most monitoring data, and all four mixes here)
│  ├─ Encode time on a hot path? (AVX-512 timings; see the note below the tree)
│  │  ├─ Readers know ALP, and neither mostly-constant nor repeating full-precision metrics dominate
│  │  │  → Shared DeltaPacked + ALP: 2.822, 1.43× Chimp's encode time (ALP-RLE 1.82×)
│  │  │    (traps: sparse_constant 1.244 against Chimp's 0.742; mix_fullprec 20.1% above Chimp)
│  │  └─ Otherwise → Shared DeltaPacked + Chimp: 3.846, encode 173,061 ns/op
│  └─ No → which codecs do your readers know?
│     ├─ ALP-RLE          → Shared DeltaPacked + ALP-RLE: 2.593, 32.6% below Chimp
│     ├─ ALP, not ALP-RLE → Shared DeltaPacked + ALP: 2.822, 26.6% below Chimp,
│     │                     unless full-precision metrics repeat (mix_fullprec: 20.1% above Chimp)
│     │                     or mostly-constant metrics dominate (sparse_constant: 1.244 against 0.742)
│     └─ Neither          → Shared DeltaPacked + Chimp: 3.846
├─ Full-precision values without repeats (worst_case)
│  └─ Shared DeltaPacked + Chimp: 6.384; ALP-RLE is 2.0% larger and takes 1.44× its encode time
└─ 5 points per metric or fewer
   └─ Shared DeltaPacked + Chimp: 8.364 at 5 points, against 8.770 for ALP-RLE
      (ALP-RLE is smaller at 10 points; 6 to 9 were not measured)

Heavy random access favors ALP or ALP-RLE on every branch: ValueAt takes 1,864 and 2,151 ns/op
per 100 lookups, Chimp 48,707 (on worst_case, ALP-RLE is 32.8× faster for 2.0% more bytes).
```

The encode figures come from CPUs with AVX-512DQ, where the encoder searches ALP's exponents with vector kernels;
elsewhere it runs the scalar search,
and ALP and ALP-RLE encode several times slower than these tables show
(see [the search design](specs/alp-simd-ef-search-design.md#results)).
On the Chimp leaves, Shared Delta timestamps take the same space (3.844 against 3.846 on `mix_monitoring`)
and their iteration is equivalent under the comparison rule, so either timestamp encoding serves.
